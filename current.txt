# Current Slice: Prepared Handle Lifecycle Truth

Owner: workspace root.

Source scratchpad:

- `render-surface-hardening-scratchpad.md`
- Promoted item: `Slice B: Prepared Handle Lifecycle Truth`

## Goal

Replace implicit raw-pointer prepared-handle lifetime with explicit owner-managed live-state discipline.

This slice exists because `HowlRenderPreparedSurfaceHandle` currently behaves like a raw pointer to an owned prepared surface. `release()` frees the object immediately, while other ABI functions later cast the same opaque pointer back into an owner. That makes release-after-use, submit-after-release, and stale cached handles unprovable at the ABI seam.

## Current Bad Shape

Current code:

- `prepared_surface_owner.Owner.fromHandle()` blindly casts a non-null opaque handle.
- `prepared_surface_ffi.release()` calls `owner.destroy()` immediately.
- `prepared_surface_ffi.describe/buffer/diagnostics()` dereference any non-null handle.
- `surface_text_ffi.publishPreparedHandle()` stores a raw prepared handle in `prepared_publish_handle`.
- `surface_text_ffi.takeSubmitHandle()` moves that raw handle into `prepared_submit_handle`.
- `surface_text_ffi.submitHandle()` consumes `prepared_submit_handle`, calls `submitOwned()`, and `submitOwned()` destroys the owner.
- `surface_text_ffi.submit()` can also submit a prepared handle directly and `Owner.submit()` eventually destroys it through `submitOwned()`.
- `SurfaceTextOwner.destroy()` does not centrally retire or free outstanding prepared-handle records.

Observed consequence:

- The ABI cannot safely reject a released handle because the object was freed.
- A handle can remain cached in `prepared_publish_handle` or `prepared_submit_handle` after external release unless the code explicitly clears it.
- A submitted/consumed handle has no explicit state; it is only gone by convention.

## Reference-Derived Rule

- Ghostty uses opaque C handles, but owner methods reject invalid values before owner mutation and keep C-facing object ownership clear.
- Alacritty keeps runtime/presentation ownership centralized instead of letting leaf helpers own lifecycle policy.
- TigerBeetle requires explicit state, pair assertions, and positive/negative tests for invalid data becoming invalid. A freed pointer cannot be inspected, so “released” must be represented as state before memory is reclaimed.

## Required Model

Use an explicit prepared-handle state owned by `prepared_surface_owner.Owner`.

Minimum state names:

- `prepared`
- `published`
- `submit_ready`
- `released`
- `consumed`

Allowed transitions:

- `prepared -> published` when `publishPreparedHandle()` accepts it
- `published -> submit_ready` when `takeSubmitHandle()` returns it
- `prepared -> consumed` when direct `submit()` succeeds
- `submit_ready -> consumed` when `submitHandle()` succeeds
- `prepared/published/submit_ready -> released` when `prepared_surface_ffi.release()` is called

Rejected transitions:

- release after `released` or `consumed` must be a no-op
- publish after `released` or `consumed` must fail
- take-submit for a stale released/consumed published handle must fail and clear cached handle state
- submit after `released` must fail
- submit after `consumed` must fail
- double-submit must fail
- cross-session handle use must fail

Memory/lifetime rule:

- `release()` must not immediately free the handle record if callers may still pass the opaque handle back.
- It may deinit the heavy prepared payload and RGBA buffer exactly once, but the handle record must remain inspectable until the owning `SurfaceTextOwner` is destroyed.
- `SurfaceTextOwner` must own and free all prepared-handle records during `destroy()`.
- A prepared handle belongs to exactly one `SurfaceTextOwner`.

This means the object shell remains alive after `release()`/`consumed`; that is intentional for ABI safety. Do not leak shells on surface teardown.

## Implementation Guidance

Prefer this shape unless code proves a smaller equally safe shape:

- Add lifecycle state to `prepared_surface_owner.Owner`.
- Add a small owner-managed registry/list of prepared handles to `SurfaceTextOwner`.
- `Owner.create()` registers the new prepared owner with `SurfaceTextOwner`.
- `SurfaceTextOwner.destroy()` retires/frees all registered prepared owners.
- `Owner.release()` marks `released` and deinitializes owned prepared payload/buffer once.
- `Owner.consumeAfterSubmit()` or equivalent marks `consumed` and deinitializes owned prepared payload/buffer once.
- `Owner.destroy()` is only used by the owning `SurfaceTextOwner` teardown path once the shell is no longer ABI-visible.
- `fromHandle()` can still cast a non-null pointer, but all public entrypoints must check state before using payload.

Payload deinit requirement:

- Do not call `prepared.deinit()` twice.
- Do not free `rgba_pixels` twice.
- Do not call `session.submitSurface(&self.prepared, ...)` after payload was released or consumed.

Cached handle cleanup requirement:

- Releasing a handle must clear `session_owner.prepared_publish_handle` if it points at that handle.
- Releasing a handle must clear `session_owner.prepared_submit_handle` if it points at that handle.
- Consuming a handle must clear matching cached handle slots.

Status behavior:

- Null prepared-surface handle remains `missing_handle` for describe/buffer/diagnostics.
- Non-null but `released`/`consumed` prepared-surface handle must return `invalid_argument` for describe/buffer/diagnostics.
- `publishPreparedHandle()` with released/consumed handle returns `HOWL_RENDER_CALL_INVALID_ARGUMENT`.
- `takeSubmitHandle()` must not return released/consumed handles.
- `submit()`/`submitHandle()` with released/consumed handle returns `.failed`.
- `release()` remains void and idempotent.

## Required Proofs

Add or update ABI tests. Prefer `src/test_abi.zig` for shipped C ABI behavior. Use `src/ffi.zig` only if an existing internal export test is the smaller fit.

Required tests:

- live prepared handle can `describe`, `buffer`, and `diagnostics`
- released prepared handle rejects `describe`, `buffer`, and `diagnostics` with `invalid_argument`
- release is idempotent and does not crash
- publish-after-release returns `HOWL_RENDER_CALL_INVALID_ARGUMENT`
- take-submit after releasing a published handle fails and does not return the released handle
- direct submit after release returns `.failed`
- successful direct submit consumes the handle, and a second direct submit fails
- successful handle submit consumes the handle, and a second `submitHandle()` fails
- cross-session publish/submit remains rejected
- surface teardown with outstanding prepared handles does not leak or double-free under the test allocator

If a proof is too large for this slice, stop and report the blocker. Do not silently skip it.

## Rejection Gates

Reject the worker diff if any of these happen:

- `release()` still frees the handle record immediately.
- Any public prepared-handle entrypoint can dereference released/consumed payload.
- A released handle can still be published, submitted, described, buffered, or diagnosed as live.
- A consumed handle can still be submitted again.
- Cached `prepared_publish_handle` or `prepared_submit_handle` can point at released/consumed handles after release/consume.
- Public ABI/header shape changes without explicit approval.
- Host/VT/present/upload changes are mixed into this slice.
- Tests rely on null handles instead of real prepared handles for lifecycle behavior.

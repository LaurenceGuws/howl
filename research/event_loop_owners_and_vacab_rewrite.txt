Verdict for eventloop:

Reference-backed shape:
term/PTY thread(s)
  mutate terminal state
  produce render-surface update readiness
  send present trigger / wake to main

main/window thread
  owns SDL pump
  owns wake coalescing
  owns layout batching
  owns texture/GL presentation
  owns frame cadence

render
  owns surface contents/contracts
  no texture vocab

layout
  runs on main for now
  batches visible surface updates into present work
  owns placement/z-order/visibility

texture
  runs on main for now
  consumes batched surface presentation work
  owns GL resources and draw/present
This matches references better:
- Alacritty: PTY thread wakes main; main batches/draws/presents.
- Foot: main loop gathers refresh flags and presents when frame callback allows.
- Kitty: IO thread coalesces wakeups; main render loop batches visible windows/tab bar and swaps.
- Ghostty: renderer thread exists, but even it has app-thread draw fallback. So copying a separate presentation thread is not required and may be wrong for SDL/GL.
So the corrected product direction:
- No layout/presentation middle thread now.
- Main thread is the presentation scheduler.
- Surfaces/terms emit present triggers to main.
- Main drains/coalesces triggers, computes layout, batches visible surface present work, and calls texture/GL.
- Texture present remains host/main-thread owned.
This also means:
- events/event.zig / main loop is allowed to be the batching control spine.
- events/scheduler.zig remains timer/deadline owner only.
- layout/ is not a thread; it is main-thread policy/data for placement and batching.
- term.zig should not know texture, but it can trigger “surface present needed” to main.
- The present trigger can live as a wake edge associated with a surface/update, not as texture state in term.
For bucket killing, the target becomes clearer:
- Remove texture state from bucket into main-thread presentation/texture owner.
- Keep term as PTY/VT/render-surface producer.
- Main/tab/layout owns batching and placement.
- Texture owns GL resource details.
The next code direction should be small:
1. Rename/reframe existing present_surface_trigger as a main-thread wake/present trigger, not texture-owned.
2. Move GL resource fields out of bucket toward texture//main presentation owner, not term.
3. Keep layout batching on main; do not introduce a thread.
This is more source-backed and less speculative.

Howl middle-path interpretation
The user’s proposed shape is directionally consistent with references in boundaries, but not fully source-backed in thread topology.
Source-backed parts
1. Term/render API must drop texture vocabulary.
- Project law already says host owns backend resource realization and texture ownership.
- Alacritty Display owns GL surface/context/renderer details.
- Ghostty Surface separates terminal surface from runtime placement.
- Foot and Kitty keep presentation/backend in host/app loop.
2. Render owns surface types / render consequences, host consumes them.
- Alacritty: terminal state → renderable content → Display draws.
- Ghostty: terminal/render.zig is renderer-neutral render state, while renderer thread/backend consumes it.
- Howl should keep howl-render surface contracts renderer-neutral.
3. Term emits metadata for tab bar / scrollbar rather than owning texture.
- Ghostty apprt/surface.zig has messages for scrollbar, title, progress, bell, pwd, child exit.
- Kitty tab/window models use metadata to update tab bar/layout/render data.
- This supports term/VT emitting metadata events, not texture resources.
4. Batch surface updates before presentation.
- Foot delayed render and pending frame callback model is strong evidence.
- Kitty input_delay and repaint_delay are strong evidence.
- Alacritty dirty/frame gating is strong evidence.
5. Layout between surface updates and texture present.
- Kitty supports layout as the owner between windows/panes and OS-window rendering.
- Foot supports “refresh flags/pending flags” before actual render.
- Alacritty supports DisplayUpdate and pending_renderer_update split.
Product-specific / invented parts
1. One presentation scheduling/owning thread for all visible surface updates is not directly found in Alacritty, Ghostty, Foot, or Kitty.
- Alacritty: main thread presentation.
- Ghostty: renderer thread per surface, with app-thread draw fallback.
- Foot: main FDM hook and Wayland frame callback.
- Kitty: main render loop over OS windows.
2. SDL user events as cross-thread routing are platform/backend-specific and not source-backed by the terminal references. They may be acceptable host details, but should not shape ABI or render owners.
3. layout.zig as thread2 needs more proof. References support layout/presentation as an owner, but not necessarily as its own OS thread.
4. texture.zig defining how and when GL draws per surface_type is acceptable only if it is host/backend-owned. It must not become the renderer architecture. Alacritty’s Display and Kitty’s render loop are better naming pressure than generic texture.

- Building a new “layout thread” before the owner contract is proven in single-threaded form.
- Adding pane before defining what a surface update is and who schedules present.
- Adding tab bar / scrollbar threads before metadata event contracts are explicit.
- Creating generic Context, State, Options, Manager, Engine, or Controller buckets.
Open questions for user
1. Is the “one presentation scheduling thread” a hard product direction, or an experiment to be proven after the owner boundaries are cleaned?
2. Must actual GL calls happen on SDL/main thread, or can the backend create/move a GL context to a presentation thread on all supported platforms?
3. Should layout.zig own only scheduling and batching, or also pane/tab geometry?
4. Are tab bar and scrollbar render surfaces part of howl-render ABI, or host-local UI surfaces fed by VT metadata?
5. Should each terminal have its own PTY/VT thread, or should Howl eventually have a Kitty-like child monitor over many terminal instances?
6. What is the minimum ABI event that represents “surface updated”: dirty rows, snapshot token, metadata event, or opaque render-surface ready?
Risks / stop conditions
- Stop if a worker tries to implement a global presentation thread without a recorded reference gap and explicit user approval.
- Stop if term/render ABI exposes texture, GL, SDL, or backend resource vocabulary.
- Stop if layout.zig becomes a bucket for pane geometry, surface batching, texture present, tab bar, scrollbar, and terminal metadata.
- Stop if pane is introduced before terminal surface/update ownership is separated.
- Stop if host code imports internal terminal modules in Zig-shaped convenience form instead of C ABI contracts.
- Stop if the design hides ownership behind manager, engine, controller, types, Context, State, or Options.
